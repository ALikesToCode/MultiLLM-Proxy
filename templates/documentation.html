Four steps from keys to a response

The same steps work locally, in the container and behind the Cloudflare Worker.

  1. Store provider keys on the server

    Use .env.local for local runs or Wrangler secrets for Cloudflare. Never put upstream keys in a browser or client app.

  2. Issue one MultiLLM client key

    Clients authenticate with an admin or user API key. MultiLLM selects the matching server-side provider credential.

  3. Discover exact model IDs

    Call /v1/models. Administrators can refresh provider catalogs from Operations before choosing a model.

  4. Choose the contract

    Use provider:model for explicit chat or images, auto:name for chat failover, or a provider prefix for native fidelity.

Failover advances only after 401, 402, 403, 404, 429, or a local open/half-open circuit response. Ambiguous timeouts and generic upstream 5xx responses are not replayed. GLM-5.2 defaults to maximum reasoning; semantic max maps to each provider's supported ceiling, while an explicit lower effort is preserved.

Long GLM-5.2 contexts use safe adaptive preprocessing by default. Configure GLM_AUTO_OPTIMIZE, GLM_AUTO_OPTIMIZE_TRIGGER_TOKENS (default 8000) and GLM_AUTO_OPTIMIZE_KEEP_RECENT_TURNS (default 8). The bounded process-local analysis cache uses SHA-256 keys plus prompt-span offsets only; it never stores conversation text or generated replies. Configure its lifetime with CONTEXT_ANALYSIS_CACHE_TTL_SECONDS (default 300) and size with CONTEXT_ANALYSIS_CACHE_MAX_ENTRIES (default 2048).

Provider prompt caching activates above PROMPT_CACHE_MIN_TOKENS (default 1024) when PROMPT_CACHE_ENABLED=true. MultiLLM sends only a provider-supported cache hint or preserves an unchanged schema for automatic-prefix providers. It never stores or replays generated responses, and raw provider routes stay caller-controlled.
